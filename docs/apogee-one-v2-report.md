# Apogee ONE v2 분석 종합 보고서

작성 2026-10-01. 대상: Apogee ONE 2세대("ONE for iPad & Mac" 2013 / "ONE for Mac" 2016), USB `0x0C60:0x0017`, 제품 문자열 `ONEv2`, 펌웨어 `1.05`.

태그: **[확인]** 로컬 바이너리·디스크립터·커널 소스 등 1차 근거로 직접 검증 / **[문서]** Apogee·MS 등 공식 문서 근거 / **[추정]** 정황 근거, 미확인.

---

## 0. 한 줄 결론

세 가지 목표 모두 길이 있다. (1) **입력 소스 전환은 Apogee 소프트웨어 없이 가능하다** — 그 명령 바이트를 Apogee 자신의 펌웨어 업데이터에서 그대로 복원했다. (2) 맥은 지금도 클래스 호환으로 동작하고, 리눅스는 독점 초기화+워치독 킵얼라이브(0x29를 4초마다)를 주면 최소 녹음까지 되는 공개 선례가 있다. 윈도우 내장 드라이버 거부는 디스크립터 결함, 초기화 누락, 워치독 누락이 섞인 문제로 아직 분리 안 됨. (3) 펌웨어 개조는 **원리적으로 열려 있다** — 업데이트 프로토콜·이미지·이중뱅크 구조를 모두 확보했고 암호화도 없다. MCU는 **Atmel AVR32-A(UC3A3/UC3A4 계열)** 로 **확정**됐다. 실제 디스어셈블러(pypcode = Ghidra AVR32 디코더)가 리셋 벡터·프로그램 시작점·`_stext` 세 앵커를 모두 ASF UC3 스타트업 코드로 복원했고, 스택 톱 `0x10000`은 내부 SRAM 64 KB(UC3A3/A4)와 일치한다(8절). 정확한 품번(플래시 용량, S 접미사)만 각인/IDCODE로 남았다.

---

> **갱신 2026-10-01:** 외부 연구 노트를 1차 소스와 대조 검증했다(별도 문서 `external-notes-verification.md`). 두 가지 중요한 추가. (1) **리눅스 동작 공개 선례가 있다** — `github.com/stevebrodie/apogee-one2-linux`(2026)가 독점 초기화 시퀀스와 **워치독 킵얼라이브**를 역설계했다. 기기는 `0x29` 6바이트 읽기를 **4초마다** 받지 못하면 약 9초 뒤 USB에서 스스로 끊는다. 이 `0x29`는 우리가 찾은 `GetHardwareChanges`와 바이트 단위로 동일하다. (2) 그 결과 **윈도우 실패 원인을 "디스크립터 결함" 하나로 단정하면 안 된다** — (가)디스크립터 비호환, (나)초기화 누락, (다)워치독 누락을 분리해야 한다. 아래 4절 서술을 이에 맞게 읽을 것.

## 1. 기기 식별과 현재 상태

- 이 기기는 2세대 ONE이다. 2009년 원조 ONE(`PID 0x0003`, UAC1, 48 kHz)과는 하드웨어가 다르다. **[확인]**
- 스스로를 **USB Audio Class 2.0** 복합 장치로 선언한다. "USB 컴플라이언스로 동작 안 함"은 절반만 맞다. 표준을 표방하되 디스크립터에 결함이 있어 **윈도우 내장 드라이버만 거부**한다. **[확인]**
- 윈도우 현상: 내장 `usbaudio2.sys`가 바인딩되지만 시작 실패(코드 10, 상태 `0xC0440022`). 이 PC의 `UsbFlags\0C6000170105` osvc = `{0,0}`. **[확인]**

### USB 토폴로지 (로컬 덤프, `usb-descriptors-0c60-0017.txt`)

- IF0 AudioControl(UAC2). 클록 소스 1개.
- 재생: USB 입력 터미널 2 → 피처유닛 4(음소거/볼륨 r/w) → 스피커 출력 3.
- **녹음: 마이크 입력 터미널 3개(9/11/13) → 피처유닛 10/12/14(볼륨 읽기전용) → 셀렉터 유닛 15(3입력, 읽기/쓰기) → USB 출력 8.** 이 셀렉터 3입력이 Int Mic / Ext Mic / Ext Mic 48V에 대응한다. **[확인]**
- IF1/IF2 오디오 스트리밍(24비트/32비트 슬롯, 동기식 iso).
- **IF3 벤더 전용(클래스 `0xFF`/서브 `0xF0`): 벌크 OUT/IN + 인터럽트 IN.** Maestro 제어·iAP(아이폰 연동) 채널. **[확인]**

## 2. OS별 지원 현황

| OS | 공식 입장 | 실제 | 근거 |
|---|---|---|---|
| macOS (Intel·Apple Silicon, ~Sequoia/Tahoe) | 지원. Apple Silicon·Big Sur+는 Control 2 필요 | **클래스 호환으로 드라이버 없이도 소리 남.** Tahoe는 "동작 예상" 그룹(테스트 안 됨) | [문서] |
| Windows 10/11 | Apogee 자체 드라이버(Thesycon 기반) 필요 | 드라이버 설치 시 동작. **내장 드라이버만으로는 코드 10** | [확인]/[문서] |
| Linux | 공식 미지원, 커널에 0x0c60 쿼크 없음 | 열거 직후 **0.5초 뒤 자가 분리 반복** 보고 다수 | [문서]/[확인] |
| iOS/iPadOS | Lightning 구형까지. USB-C는 "입력 안 잡힘", iOS 26은 Lightning서도 실패 | 사실상 종료 수순 | [문서] |

- **지원 전망:** ONE은 Apogee KB의 "Legacy Products"로 분류됐고 일본 유통사는 생산완료로 표기. 공식 EOL 날짜는 없음. Maestro 2(맥)는 Intel 전용으로 동결, Apple Silicon은 Control 2로 이관. 윈도우 드라이버(Thesycon)는 2024-09의 5.68.0까지 나왔고 Win11 24H2까지 서명됨. **드라이버가 끊기면 이 기기는 "표준 클래스로 안 잡히는" 특성 때문에 OS 업데이트에 취약하다.** 이것이 사용자의 우려가 타당한 지점이다. **[문서]**
- 이 PC에는 **설치형 Control 2(Win 1.21.49)가 이미 bin 폴더에 있다.** Thesycon 드라이버를 깔면 지금 당장 윈도우에서 동작시킬 수 있다. 다만 목표는 "소프트웨어 없이"이므로 아래 3~4절이 본론이다. **[확인]**

## 3. 핵심 발견: 입력 전환 명령을 Apogee 코드에서 그대로 복원했다

사용자가 받아둔 Maestro **2.5C DMG** 안의 `One Firmware Updater.app`에는 디버그 심볼이 살아 있었다. `ONEv2USB` 클래스 전체 메서드와 그 USB 요청 래퍼(`ONEv2USB::USBRequest`)를 디스어셈블해 **전 제어 프로토콜을 바이트 단위로 복원**했다. **[확인]**

**요청 형식:** EP0 벤더 요청. `bmRequestType = 0x40`(쓰기) 또는 `0xC0`(읽기), `wValue = 0`, `wIndex = 0`, 데이터 1바이트(믹서 계열만 채널 인덱스 사용).

### ONEv2 벤더 요청 표 (전량, 디스어셈블로 확인)

| bRequest | 기능 | 데이터 |
|---|---|---|
| **0x36** | **마이크 입력 타입** | **0=내장 마이크, 1=외장 마이크, 2=외장+48V** |
| 0x34 | 마이크 프리앰프 게인 | signed byte(dB) |
| 0x3E | 악기 입력 게인 | signed byte |
| 0x44 | 두 입력 게인 그룹 | bool |
| 0x35 | 출력 음소거 | bool |
| 0x33 | 출력 감쇠 | byte |
| 0x53 | 출력 라우트(소스) | enum |
| 0xB6 | 출력 기준 레벨 | enum (wIndex=채널) |
| 0x26 | Identify(LED 점멸) | bool |
| **0x48** | **인코더(노브) 선택 상태 읽기** | byte |
| **0x29** | **하드웨어 변경 이벤트 읽기** | 6 bytes |
| 0x14 | 미터 데이터 | 16 bytes |
| 0x1F/0x20 | 미터 피크/오버 홀드 | byte |
| 0x27 | 미터 클리어 | — |
| 0x28 | 펌웨어 버전 / 하드웨어 고유 ID | 3 bytes |
| 0x3F | 세션 토큰 | byte |
| 0x52 | 서스펜드 이벤트 / 장치 프리픽스 | byte |
| 0x4C–0x4F | 믹서 페이더/팬/솔로/뮤트 | wIndex=채널 |

입력 타입 enum 0/1/2는 펌웨어 내 표시 문자열 "Internal Mic + Instrument / External Mic + Instrument / External 48V + Instrument" 순서로 추정했다. **쓰기 전에 반드시 읽기(0xC0,0x36)로 현재값을 먼저 확인**하면 안전하게 매핑을 검증할 수 있다. **[확인/추정]**

### 바로 쓸 수 있는 방법 (소프트웨어 없이)

1. **벤더 명령 직접 전송** — `resources/onev2_input_switch.py`(pyusb). 리눅스에서는 벤더 요청이 커널 드라이버 분리 없이 통과하므로 `snd-usb-audio`와 공존한다. 맥에서도 동작한다. 성공하면 **OLED 아이콘이 내장↔외장으로 바뀐다.** 윈도우에서는 WinUSB 바인딩 후 가능(4절). **[확인]**
2. **macOS 네이티브** — 셀렉터 유닛 15는 표준이라 CoreAudio가 입력 소스로 노출한다. 오디오 MIDI 설정의 입력 소스 팝업에서 Maestro 없이 Int/Ext를 고를 수 있을 가능성이 높다. (Apogee KB도 "시스템 설정 > 사운드 > 입력에서 입력 타입 조정 가능"이라 명시.) Control 2가 까는 `ONEv2USBOverideDriver.kext`는 **코드 없는 더미(지연시간·이름만 추가)**라, 맥 오디오는 애플 클래스 드라이버가 처리한다. 즉 맥은 이미 "소프트웨어 없이 거의 다 된다". **[확인/문서]**
3. **리눅스 자가분리 루프 주의** — 열거 직후 호스트의 `0xEE`(MS OS 문자열) 요청, 즉 libmtp의 `mtp-probe`가 방아쇠라는 가설. udev 규칙 `ATTR{idVendor}=="0c60", ATTR{idProduct}=="0017", ENV{MTP_NO_PROBE}="1"`를 먼저 적용해 볼 것. **[추정]**

## 4. 윈도우에서 왜 거부되는가 + 직접 시험 절차

- `0xC0440022` = `usbaudio2.sys` 자체 메시지 테이블의 **이벤트 ID 34 "장치가 보고한 USB 디스크립터가 사양에 부합하지 않거나 드라이버가 지원하지 않음"**. 로컬 이벤트 로그에서 확인(플러그인마다 1건). 정적 디스크립터 검증 단계에서 멈추며, 동기식 엔드포인트·클록 요청 등은 원인이 아니다. **[확인]**
- 유력 결함 후보(클린 펌웨어라면 모두 고쳐야 함):
  1. **CLOCK_SOURCE id 1 중복 선언** (UAC2 위반)
  2. **IAD가 벤더 IF3까지 포함** (오디오 컬렉션은 AC/AS/MIDI만 허용)
  3. **피처유닛 4/10/12/14의 bLength가 10** (2채널이면 18이어야 함)
  4. **AC 헤더 wTotalLength 174** (실제 167, 엔드포인트 7바이트 오산입)
  정확히 어느 검사가 걸리는지는 관리자 권한 WPP 트레이스가 필요하나, 26100용 TMF가 공개되지 않아 사실상 MS 외부에서 해독 불가. **[확인/추정]**
- **무드라이버 우회는 사실상 없음:** 레지스트리 노브 없음, 디스크립터 패치 필터는 서명 문제, 결국 Thesycon 드라이버·펌웨어 수정·테스트서명 필터 중 택일. **[확인]**
- **직접 시험(되돌리기 가능):** Zadig로 부모 복합 노드에 WinUSB 바인딩(관리자 권한 필요) → `onev2_input_switch.py`로 0x36 읽기/쓰기. 윈도우에선 오디오는 안 나와도 **입력 전환 명령과 노브 상태 읽기는 검증 가능**. 되돌리기는 장치 관리자 "디바이스 제거 + 드라이버 삭제" 후 재연결. **이 작업은 사용자 승인(관리자 UAC)이 필요하므로 진행 전 확인받겠다.** **[확인]**

## 5. 펌웨어: 업데이터·이미지·프로토콜을 모두 확보했다

- Maestro 2.5C DMG에서 추출 완료, `resources/firmware-maestro-2.5C/`에 저장:
  - `ONEv2_USB_Audio_Image0.bin` (96 KB), `ONEv2_USB_Audio_Image1.bin` (224 KB) — **펌웨어 버전 1.5.0 = 기기의 1.05.** 즉 사용자 기기는 이미 최종 펌웨어. **[확인]**
  - `One_Firmware_Updater.macho` — 심볼 포함. 플래시 프로토콜 전체가 여기서 나왔다.
  - 두 이미지는 **이중 뱅크(A/B)** 구조이고 본문 오프셋 `0x7e1`에서 1바이트만 다름(뱅크 ID 등). 펌웨어가 항상 양호한 사본을 유지하므로 **잘못된 플래시는 복구 가능**. **[확인]**
- **업데이트 전송 방식:** 전용 벤더 DFU. `ApoUSB` 클래스에 `EnterDFU / StartDFU / WriteDFUBlock / ReadDFUStatus / EndDFU / SelectFirmwareID / EraseFirmware`와 `VendorSpecificReset / SetImageType / SetRevertId / FinalizeBootPartition`가 있다. 플래시 시 **PID 0x8017("Apogee ONE DFU")로 재열거**. "Active image is %d" 로그 = 뱅크 전환. **[확인]**
- **암호화 없음:** 이미지 엔트로피 약 6.9(평문 컴파일 코드). 디스크립터 테이블이 평문으로 박혀 있다(기기에서 뜬 것과 동일한 config 디스크립터가 이미지 내 `0x17614`에 존재). **따라서 §4의 디스크립터 결함 4종 수정은 순수 데이터 패치**다. **[확인]**
- **명령어 집합 = AVR32.** 대조군을 둔 패턴 시험 결과(10 KB당). AVR32 GCC 프롤로그 `EBCD4080` 5.6, 에필로그 `E3CD8080` 9.5회가 나왔다. 반면 ARM 양성대조(Duet3.bin, Boom.bin)에서는 이 패턴이 0회였고, 대신 Thumb `bx lr`가 21~26회 나왔다. ONE 펌웨어의 Thumb/ARM 패턴은 0회다. 진짜 랜덤과 바이트 셔플본에서는 AVR32 패턴이 0회다. **[확인]**
  - 처음 돌린 시험들은 랜덤 대조군 코드에 버그가 있었다(같은 바이트 반복). 위 수치는 수정한 재시험 결과다.
  - "포인터가 함수 시작점에 떨어지는가" 시험은 포인터 후보 선정이 엉성해 **판단 불가**로 처리한다.
  - 이미지 첫 4바이트를 AVR32 분기로 본 해석은 사후 끼워맞춤이라 근거로 쓰지 않는다.
- **칩 계열:** Atmel 상표(사용자가 고해상도 기준 사진으로 독립 대조) + AVR32 코드 + 하이스피드 USB 장치 컨트롤러 → **AVR32 UC3A3 또는 UC3A4.** 정확한 품번(플래시 128/256 KB 등)은 각인 확인 전까지 **[추정]**.
- **이미지 구조와 베이스 주소 [확인]:** 파일 오프셋 0 = 플래시 `0x80000000`이다. 근거는 두 가지 독립 시험이다. (1) 펌웨어 내 문자열 17개 중 5개("Internal Mic + Instrument" 등 입력 이름 3개 포함)가 정확히 `0x80000000 + 파일오프셋` 값의 빅엔디언 32비트 포인터로 참조되며, 다른 어떤 베이스나 리틀엔디언으로는 0개다. (2) 뱅크0/뱅크1 이미지의 차이 662바이트 **전부**가 `0x80004000~0x80024000` 범위 빅엔디언 절대주소에 `+0x20000`을 더한 재배치로 설명된다. 즉 같은 코드를 `0x80004000`(뱅크0)과 `0x80024000`(뱅크1) 두 베이스로 링크한 위치의존 이미지이고, 앞 `0x4000`은 업데이트가 건드리지 않는 부트로더 영역이다.
- **DFU 모드는 부트로더에 있다 [확인]:** 앱 이미지 어디에도 PID `0x8017`이나 DFU 인터페이스 디스크립터가 없다. 복구 경로는 업데이트 파일에 포함되지 않은 부트로더가 담당한다. 부트로더는 우리 손에 없으므로 **부트로더를 손상시키면 복구 수단이 사라진다.**
- **체크섬 [확인]:** 이미지 꼬리 4바이트(`0x00000A94`)는 내용이 다른 두 뱅크 이미지에서 동일하므로 내용 체크섬이 아니다. 업데이터는 페이지 단위 읽기 비교로 검증한다("Flash page did not match"). 부트로더가 별도 검증을 하는지는 미확인.
- **디스크립터 테이블 [확인]:** 기기 디스크립터(`0x175F4`), 디바이스 퀄리파이어, 동일한 config 디스크립터 사본 2개(`0x17614`, `0x17768`), USB 문자열 테이블(iInterface 17 = "iAP Interface", iTerminal 18/19/20 = 입력 이름 3개)이 평문으로 있다. 패치 시 뱅크별로 따로 적용해야 한다.

### 펌웨어 개조 타당성

- **(A) 디스크립터 결함만 수정해 "클린 클래스 호환"으로 만들기:** 평문 데이터 패치. 이미지 CRC(말미 4바이트·페이지 검증)만 재계산하면 됨. 난이도 중. **윈도우 내장 드라이버로도 잡히게 만드는 가장 현실적인 목표.**
- **(B) 노브 제스처(더블/트리플클릭·롱프레스)로 입력 전환:** 코드 패치. 펌웨어는 **이미 인코더를 읽는다**(부팅 시 노브 길게=공장초기화, `GetEncoderSelect`/`GetHardwareChanges`로 이벤트 노출). 즉 인코더 핸들러에 "제스처 감지 → 내부적으로 입력 타입 순환" 로직을 추가하는 일. MCU 식별과 펌웨어 디스어셈블이 선행돼야 함. 난이도 상.
- **리스크/복구:** 이중 뱅크라 비활성 뱅크로의 잘못된 쓰기는 Apogee 부트로더가 살아 있는 한 복구 가능. 펌웨어가 MCU 내부 플래시에 있는지 외장 플래시에 있는지는 **칩 확정 전까지 모른다.** 어느 쪽이든 원칙은 같다. 무엇을 쓰기 전에 현재 내용을 백업할 수단(JTAG 등)을 먼저 확보하고, 읽기 보호가 걸려 있는지 확인하고, 확인 전에는 어떤 지우기도 하지 않는다. **[추정]**

## 6. 다음 단계 권장

**오늘 당장 (소프트웨어 설치 없이):**
1. **맥에 연결** → 오디오 MIDI 설정에서 입력 소스에 Int/Ext가 뜨는지 확인. 뜨면 목표 2는 맥에서 이미 해결.
2. 맥이나 리눅스에서 `resources/onev2_input_switch.py` 실행 → `0xC0,0x36` 읽기로 현재 입력 확인 → `python onev2_input_switch.py 1` 로 외장 전환, **OLED 아이콘 변화로 검증.**

**며칠 단위:**
3. 이 윈도우 PC에서 노브 상태(`0x48`)·이벤트(`0x29`)를 읽어, "노브 제스처 → 벤더 0x36 전송"을 **호스트 측 작은 상주 프로그램**으로 먼저 구현. 펌웨어를 안 건드리고도 "노브로 입력 전환"을 (호스트가 켜져 있는 동안) 달성. WinUSB 바인딩은 관리자 승인 필요 — 진행 전 확인 요청.
4. 리눅스에서 udev `MTP_NO_PROBE` 규칙으로 자가분리 루프 해소 여부 확인.

**장기 (기기 단독 완결):**
5. 실물을 열어 U1 각인을 선명하게 촬영해 칩 확정 → 확정된 칩에 맞는 디스어셈블러로 이미지 해석 → 디버그 헤더 위치·핀 확인 → 백업 수단 확보 후에만 (A) 디스크립터 수정, (B) 노브 제스처 내장을 검토. 칩이 AVR32로 확정되면 같은 계열 오픈소스 UAC2 펌웨어 선례(SDR-Widget/Audio-Widget로 알려짐, 미확인)를 참고 후보로 본다.

## 8b. AVR32 확정 (실제 디스어셈블로 검증)

툴: `pip install pypcode`(Ghidra의 AVR32 디코더, 언어 ID `avr32:BE:32:default`). 설치·관리자 권한·다운로드 승인 불필요. 베이스 `0x80000000`으로 선형 디스어셈블한 결과, 세 앵커가 모두 Atmel ASF UC3 스타트업과 일치했다. **[확인]**

| 주소 | 디스어셈블 | 의미 |
|---|---|---|
| `0x80000000` | `BR 0x80004000` | 리셋 트램폴린 → 뱅크0 프로그램 시작점 |
| `0x80004000` | `SUB PC, PC, -0x2950` → `0x80006950` | ASF `program_start` → `_stext` |
| `0x80006950` | `MOV SP, 0x10000` / `MTSR EVBA, R0` / `.data`·`.bss` 루프 | ASF `startup_uc3.S` `_stext`. 스택 톱 = SRAM 64 KB 끝 |

- 스택 톱 `0x10000`(64 KB SRAM) → **UC3A3/A4 계열**. 첫 워드가 두 뱅크에서 분기 변위 1비트만 다른 것도 재확인됐다.
- 더 깊은 RE는 Ghidra 본체(무설치 zip 570 MB + 무설치 JDK 205 MB)로 함수/xref/디컴파일 가능. 알려진 스펙 결함(`ST.B` 변위 4배 오류 PR #8907 등)은 로컬 패치 가능.
- 다음 디스어셈블 목표: 벤더 요청 디스패처(요청 0x36 처리부)와 인코더 핸들러 위치 찾기.

## 8. 하드웨어 식별 (저해상도 인터넷 사진 기준, 신뢰도 낮음)

사진이 흔들리고 해상도가 낮아 **각인 판독은 대부분 신뢰할 수 없다.** 아래는 참고용이며, 실물 촬영으로 다시 확인해야 한다.

보드 실크(비교적 판독 가능): `© 2012 APOGEE ELECTRONICS CORP`, `0000-0044-0100 REV 4.0`.

| 위치 | 추정 | 신뢰도 |
|---|---|---|
| **U1** (USB 포트 아래, 마이크 캡슐에 일부 가림) | 메인 MCU. 로고는 사용자가 고해상도 Atmel 칩 사진과 대조해 **Atmel로 판단**. 펌웨어 시험(5절)과 합치면 AVR32 UC3A3/A4. 품번 줄은 판독 불가 | 상표·계열 높음, 품번 낮음 |
| **U6** | 거꾸로 된 각인이 "AKM AK4621EF"로 읽힘. AKM 오디오 코덱일 가능성 | 중간 |
| LED 블록 옆 2x5 핀 헤더 | 물리적 핀 헤더는 보임. 용도(디버그 등)는 **알 수 없음** | 헤더 존재 중간, 용도 낮음 |
| 검은 원통 | 내장 마이크 캡슐 | 중간 |
| 좌하단 | `+7VA/-7VA/+48V` 실크 → 아날로그 전원·팬텀 전원부 | 중간 |
| S1 | 노브(로터리 인코더 + 푸시) | 중간 |

**남은 확인:** 실물 U1 각인의 선명한 근접 사진으로 정확한 품번(UC3A3 vs UC3A4, 플래시 용량, 보안 기능 S 접미사)을 확정한다. 이것이 디버거·툴체인 선택과 플래시 배치 가설 검증의 출발점이다.
